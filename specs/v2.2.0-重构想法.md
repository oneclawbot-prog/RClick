对，如果确定采用 **Finder Extension + Main App + Helper 进程**，我建议架构不要搞成三个进程互相平等通信，而是明确一个中心：

> **Helper 是核心服务，Main App 是控制面，Finder Extension 是 Finder 适配层。**

这样职责最清楚。

## 推荐架构

```text
                    ┌──────────────────────┐
                    │      Main App        │
                    │    Settings / UI     │
                    │                      │
                    │ • 菜单编辑           │
                    │ • Action 配置        │
                    │ • 脚本配置           │
                    │ • 偏好设置           │
                    │ • Runtime 管理       │
                    └──────────┬───────────┘
                               │
                         ActorLink IPC
                         LocalSocket
                               │
                               ▼
┌──────────────────────┐ ┌──────────────────────┐
│  Finder Extension    │ │       Helper         │
│                      │ │   RClick Runtime     │
│ • 获取 Finder 上下文 │ │                      │
│ • 请求菜单           │◀│ • MenuService        │
│ • 创建 Finder 菜单   │ │ • ActionService      │
│ • 用户点击动作       │▶│ • ScriptService      │
│                      │ │ • ConfigService      │
└──────────┬───────────┘ │ • PluginService      │
           │             │ • IPC Server         │
           │             └──────────────────────┘
           │
           ▼
        Finder
```

核心原则是：

> **所有业务逻辑尽量只存在 Helper 一份。**

# 1. Main App：主要是 Settings，但不只是“一个配置文件编辑器”

你的理解基本对。Main App 应该是 **Settings / Control Center**。

它不应该负责：

* 生成 Finder 菜单
* 执行 Shell
* 执行具体 Action
* 常驻后台提供业务服务

它主要负责让用户**管理 RClick**。

### Main App 的职责

#### 配置

例如：

* 创建菜单
* 调整菜单顺序
* 创建 Action
* 编辑 Shell Script
* 设置图标
* 配置快捷参数
* 启用/禁用菜单项

```text
用户
 ↓
Main App UI
 ↓
Config API
 ↓
RClick Runtime
```

这里我建议**配置的最终所有权也在 Helper**。

Main App 不直接成为“配置数据库中心”，而是：

```swift
await runtime.updateConfig(config)
```

Runtime 负责验证、保存和重新加载。

这样以后即使 Main App 不启动，Runtime 仍然拥有完整状态。

---

#### 管理

Main App 还可以负责：

* 启动/停止 Runtime
* 显示 Runtime 状态
* 查看日志
* 检查版本
* 管理插件
* 导入/导出配置
* 恢复默认配置

所以更准确地说：

> **Main App = RClick 的 Settings + Management UI。**

而不仅仅是 Settings。

---

# 2. Helper：真正的 RClick 核心

我建议代码和架构中叫：

```text
RClickRuntime
```

部署层面它是 Helper / Background Process。

但从职责来说，它是 Runtime。

它应该拥有所有核心能力：

```text
RClickRuntime
│
├── IPC Server
│
├── ConfigService
│
├── MenuService
│
├── ActionService
│
├── ScriptService
│
├── PluginService
│
├── PermissionService
│
└── Logger
```

例如 Finder Extension 问：

> 当前选中了这三个文件，应该显示什么菜单？

Extension 不应该自己判断：

```swift
if file.isImage {
    ...
}
```

而是发送：

```text
MenuContext
    ↓
RClickRuntime
    ↓
MenuService
    ↓
返回 MenuDefinition
```

Finder Extension 根据结果创建 Finder 菜单。

用户点击：

```text
Finder
  ↓
Finder Extension
  ↓
ExecuteActionRequest
  ↓
RClickRuntime
  ↓
ActionService
  ↓
执行
```

这样业务逻辑全部集中在一个地方。

---

# 3. Finder Extension：应该尽可能薄

这是三个组件中最应该“克制”的一个。

它只负责 Finder API。

可以理解为：

> **Finder ↔ RClick Runtime 的 Adapter。**

它负责两类事情。

### 获取上下文

例如：

* 当前选中的文件
* 文件 URL
* 当前目录
* 是否多选
* 文件类型

然后转换成 RClick 的通用数据：

```swift
let context = SelectionContext(...)
```

发送给 Runtime。

### 渲染菜单

Runtime 返回：

```text
MenuDefinition
├── Open Terminal
├── Copy Path
├── Git
│   ├── Commit
│   └── Push
└── Custom Script
```

Finder Extension 把它转换成：

```text
NSMenu
```

因此 Finder Extension **知道 NSMenu，但 Runtime 不需要知道 NSMenu**。

这是非常重要的边界。

Runtime 最好只返回自己的模型：

```swift
struct MenuItemDefinition: Codable {
    let id: String
    let title: String
    let children: [MenuItemDefinition]
}
```

Extension 负责：

```swift
MenuItemDefinition → NSMenu
```

# 三者的责任边界

| 功能             | Main App | Finder Extension | Runtime |
| -------------- | -------- | ---------------- | ------- |
| SwiftUI 设置界面   | ✅        | ❌                | ❌       |
| 编辑菜单           | ✅ UI     | ❌                | ✅ 保存/验证 |
| 生成业务菜单         | ❌        | ❌                | ✅       |
| NSMenu 创建      | ❌        | ✅                | ❌       |
| 获取 Finder 选中文件 | ❌        | ✅                | ❌       |
| 判断哪些菜单可用       | ❌        | ❌                | ✅       |
| 执行 Action      | ❌        | ❌                | ✅       |
| 执行 Shell       | ❌        | ❌                | ✅       |
| 管理配置           | UI       | ❌                | ✅       |
| 插件加载           | UI 管理    | ❌                | ✅       |
| IPC            | Client   | Client           | Server  |

这张表基本就是整个架构的核心。

# Main App 到底应该直接读写配置文件吗？

**我的建议是不直接读写。**

例如不要这样：

```text
Main App ──────写 JSON──────► Config File
                                   ▲
                                   │
Runtime ───────────────────────────┘
```

这会产生两个问题：

1. 谁才是配置的真正拥有者？
2. Runtime 正在读取配置时，Main App 修改怎么办？

更好的方式：

```text
Main App
    │
    │ ActorLink
    ▼
ConfigService
    │
    ▼
Config Storage
```

也就是说：

> **Runtime 是唯一的业务状态 Owner。**

Main App 只是客户端。

当然 Runtime 可以把配置保存成 JSON、SQLite 或其他方式，但这是 Runtime 内部实现。

---

# 最终我推荐的职责定义

### Main App

> **Configuration & Management UI**

用户操作的控制台。

### Finder Extension

> **Finder Integration Adapter**

负责接入 Finder，不负责业务。

### RClick Runtime

> **Core Business Runtime**

真正的 RClick。

### ActorLink

> **IPC Runtime**

负责进程间通信，本身不知道 RClick 的业务。

---

所以回答你最初的问题：

> **Main App 只配置吗？**

**大体上是，但我会说得更准确一点：Main App 负责“配置和管理”，Helper 负责“运行和执行”。**

这条边界非常适合 RClick：

```text
Main App
配置、管理、观察

Finder Extension
接入、获取上下文、显示菜单

RClick Runtime
判断、处理、执行、保存状态
```

我认为这比“Main App 是核心，Helper 只是辅助进程”的架构更适合 RClick。尤其未来你增加 **Quick Action、CLI 或其他入口**时，它们都只需要变成新的 Adapter：

```text
Settings ──────┐
FinderSync ────┤
Quick Action ──┼── ActorLink ──► RClick Runtime
CLI ───────────┤
未来入口 ──────┘
```

这样三进程架构的核心不会变，扩展入口也不会导致业务逻辑重复。
